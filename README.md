# wxgame-bot — PC 微信小游戏《雷霆战机：集结》每日任务自动化

PrintWindow 截屏（窗口被遮挡也能抓到真实画面）+ OpenCV 模板匹配 + 拟人点击。
每个每日任务都是 `tools/` 下的**独立用例脚本**（自带 `--dry` 只出计划、零点击，和自己页面的模板裁剪用例），
覆盖：免费体力/扫荡卡/礼包、星际探索、扫荡关卡、BOSS 闪击、寻宝、转盘、兑换星辉、十年集结、战队捐献、好友体力、逐星补给（大部分含看广告流程）。

## 环境

Windows + PC 微信，游戏窗口客户区 **845×1521**（即模板基准尺寸 `REF_SIZE`，见下「窗口自适应」；
顶部约 100px 是微信自绘标题栏，裁模板必须避开）。窗口可被遮挡、不必前台，位置随意；
尺寸变了也能跑（匹配前会自动归一），但长期跑建议固定窗口尺寸。

```bash
uv sync                          # 安装依赖
uv run python main.py check      # 环境自检（窗口/截屏/模板/配置）
```

## 常用命令

| 命令 | 用途 |
| --- | --- |
| `uv run python main.py check` | 环境自检（窗口/截屏/模板/配置） |
| `uv run python main.py snap [名]` | 截当前游戏画面到 shots/ |
| `uv run python tools/maint/docs.py` | 按 `wb/registry.py` 重写本文档的用例清单（`--check` 只校验是否同步） |

## 窗口自适应（窗口尺寸变了怎么办）

- **坐标自适应**一直都有：窗口随意移动/被遮挡都行（`ClientToScreen` 取客户区原点 + `PrintWindow` 抓图）。
- **缩放自适应**在 `wb/bot.py::match_adaptive`。基准尺寸 `REF_SIZE = (845, 1521)`：
  - 客户区 == 基准 → 走原路径直配，**零额外开销**。
  - 客户区 ≠ 基准 → 把画面重采样回基准坐标系再匹配，命中坐标按比例反映射回真实客户区。
    4 个几何假设（拉伸铺满 / 按宽等比 / 按高等比 / 折中）取最高分，上次命中的假设缓存优先复用，
    命中够硬（≥0.97）即早退；稳态约 100ms/次，一次任务多花 ≈1s（相比广告时长可忽略）。

实测（拿 845×1521 首页快照合成各种尺寸，6 张首页模板）：

| 场景 | 裸匹配 ≥0.90 | 自适应 ≥0.90 | 自适应落点误差 |
| --- | --- | --- | --- |
| 0.65× / 0.80× / 0.90× | 0/6 | 6/6 | 0px |
| 1.10× / 1.25× | 0/6 | 6/6 | 0px |
| 等比缩放+黑边（0.8/0.9/1.1×） | 0/6 | 6/6 | ≤1px |
| 窄高 760×1519 / 宽矮 900×1400 | 1~2/6 | 6/6 | 0px |

⚠ **裸匹配不报错但会静默指错位置**（还能得 0.90~0.96 分，却偏 20~30px），比直接失配更危险。
另：今天这个窗口 845×1521 → 813×1519 时游戏是「按高度等比、宽度居中裁切」，画布只缩了 0.13%，
所以裸匹配还能到 0.96（但整体左移 15px）；真正会炸的是**高度变化**（及换机器/显示器缩放）。

三条边界：
1. **画布被裁到可视区外的部分救不回来**：窗口太窄时左右内容跑到屏幕外，属 UI 可见性问题（把窗口拉宽即可）。
2. **`REF_SIZE` 必须等于模板的来源尺寸**：改它等于全部模板要重裁；换机器/缩放建议固定窗口尺寸再跑。
3. 重建基准：新尺寸截图 → `REF_SIZE` 同步改 → 四页 `crop_*.py` 重裁。

`tools/maint/live_check.py` 每张模板都会给实际得分与落点；尺寸不一致时首行会提示
`[窗口自适应] 客户区 WxH ≠ 模板基准 845x1521，按 … 归一后匹配`。

### 坐标口径（模板命中 vs 硬编码常量）

顶部标题栏 **固定 77px 不随窗口缩放**（实测 845/812/601 三种真帧都是 77），所以「客户区」不能
按整图等比换算。统一模型（`wb/bot.py::ref_to_client` / `client_to_ref`）：

```
s = (客户区高 - 77) / (1521 - 77)        # 按客户区高比
x' = (x - 422.5) * s + 客户区宽/2          # 宽度居中
y' = 77 + (y - 77) * s
```

实测校准（用真实帧，按钮真值由模板命中/颜色环圆心量出）：按钮在 845 → (755,1296)，
812 → (738,1293)，601 → (546,977)，三点误差 ≤1px。

两类坐标**绝不能混**：

| 来源 | 空间 | 怎么点 |
| --- | --- | --- |
| 模板命中（`sc.find` / `find_all`） | **客户区**（`match_adaptive` 已反映射） | 直接 `click_at`，**不要**再换算 |
| 硬编码常量（在**某张实帧**上量的） | 先归一到**基准** | `client_to_ref(x, y, 实帧宽, 实帧高)` 写进常量 → `click_base` 点 |
| 「命中 + 偏移」（锚点自适应，偏移是常量） | 偏移量按 `scale_delta` 缩放 | `bot.scale_delta(dx, dy, 标定帧, 当前帧)` 加到命中坐标上 |
| 像素判态区域 | 基准 | `sc.roi(x, y, w, h)` |
| 拖拽 | x 客户区 / y 基准 | `drag_up()` 已内置换算 |

- 常量归一的写法（来源帧写进注释，可追溯）：
  `MAT_ICONS = [bot.client_to_ref(x, 345, 812, 1518) for x in (156, 299, 440, 582)]`
  在标定尺寸上往返**恒等**（810/812 实跑与原值差 ≤1px），601/845 才算得准。
- **偏移也必须缩放**（第三类的坑）：`missile_hunt` 里「卡标题 → 卡的闪击键」的
  偏移是在 601 实帧上量的 (301,176)，到 845 就是 (408,238)、到 812 是 (407,238)。
  若把偏移当常量直接加，小窗口会偏 100px+（同款按键有两张，偏了就点到别的卡）。
  自检 `geom_selftest` ⑦ 锁这条：偏移不随窗口缩放立刻 FAIL。
- 自检兜底：`sweep_stage_selftest` ⑫ 在 RECT=601x1143 下断言换算结果；
  `boss_mode_selftest` ⑨ 把 3 个实测尺寸写死成断言；`geom_selftest` 是总闸门。改坏换算立刻 FAIL。
- 窗口中线/边缘这类「随窗口走」的量别写死：用 `sc.w / 2`（如 `free_treasure` 分左右卡）。

  - ⚠ **别点卡片正中间**（那是插画/EXP 条），要点**底部黄色支付键**：左卡 (226,1129)、右卡 (612,1129)。
  - ⚠ **三层遮罩都得单独判层**（同为半透明遮罩，底下的页标志依然满血命中 `gd_title` 1.000 /
    支付键 0.999 ⇒ 不看它们就等于瞎点）：
    ① `gd_confirm_title`（「确定要进行」钻石/金币弹窗共用前缀）→ DIALOG；
    ② `gd_no_cnt_title` / `gd_no_cnt_ok`（「捐献次数不足」+ 绿「确认」）→ NOCNT；
    ③ 「恭喜获得」是全屏暗幕（标题被打到 0.446）→ 用 `claim_btn` 命中且 `gd_title` 不命中判定。
  - ⚠ **次数用尽不是沉默**：点黄键会弹「钻石捐献次数不足」（绿「确认」）→ 脚本收掉它再停手；
    真·沉默（点后无任何弹层）才走「丢点击重试」。不区分就会在模态弹窗上空点 3 轮、还留个弹窗在屏上。

    仍停在捐献页且**无任何弹层**才重试，最多 3 次；重试前必查状态 ⇒ 不会重复捐（自检断言「领取只点 1 次」）。

## 运行中紧急停止

把鼠标猛地甩到屏幕 **左上角 (0,0)**，FAILSAFE 立即中止整个流程。

## 风险提示

小游戏对脚本有风控检测（点击过于规律、全天在线等）。建议只在你平时玩的时段运行，
保持拟人参数（随机偏移/停顿）开启，封号风险自担。
